+## What Actually Went Wrong
+
+### 1. The route was narrowed too aggressively
+
+The latest failure was not an OpenRouter-wide failure.
+
+The main hot path was:
+
+- `ollama/minimax-m2.7:cloud`
+- then `openai-compatible/minimaxai/minimax-m2.7`
+
+Meanwhile OpenRouter was only configured with `openrouter/free`, so it was not participating as a
+strong fallback lane for the paid/non-free MiniMax path.
+
+### 2. Pinning changed the router from adaptive to brittle
+
+Per upstream `modelrelay` behavior, the intended usage is:
+
+- `auto-fastest`
+- or grouped model IDs such as `minimax-m2.5`, `kimi-k2.5`, `glm4.7`
+
+Your current exact-lane usage effectively defeated the adaptive advantage. It reduced diversity,
+increased exposure to one provider/model pair, and made 429s or route saturation much more likely
+to surface directly.
+
+### 3. Streaming error handling is structurally weak
+
+In the installed `modelrelay` server, the selected upstream response body is forwarded by:
+
+- `Readable.fromWeb(selectedResponse.body).pipe(captureStream).pipe(res)`
+
+That path does not install explicit stream error handling before piping to the response.
+
+So if the upstream provider closes the socket mid-stream, Node/Undici can emit:
+
+- `TypeError: terminated`
+- `UND_ERR_SOCKET`
+
+and the router process can die instead of degrading gracefully.
+
+### 4. Auto-update likely increased drift
+
+The upstream README states auto-update is enabled by default and checks npm periodically.
+
+That means `modelrelay` can change routing behavior, provider ordering, model availability
+assumptions, and retry behavior without you deliberately performing a controlled upgrade.
+
+If the last 2-3 days felt materially worse, one plausible cause is:
+
+- provider saturation
+- pinned narrow route
+- upstream package drift from auto-update
+
+not just one broken key.
+
+### 5. `modelrelay` is the wrong product boundary for Nexus canon
+
+The upstream package is optimized for:
+
+- free-model routing
+- coding-friendly dynamic model selection
+- convenience routing
+
+Nexus needs more than that. Nexus needs:
+
+- route governance
+- trust-aware lane selection
+- evidence-aware benchmark weighting
+- durable audit
+- memory-backed route learning
+- joker/local/foundry runtime unification
+
+That is larger than `modelrelay`'s intended responsibility.
+

+## Why It Gives "0 Performance Boost" Now
+
+There are five likely reasons:
+
+1. The route is pinned enough that the adaptive router cannot use its core advantage.
+2. OpenRouter is only configured for `openrouter/free`, so it does not cover the high-pressure path.
+3. The relay is mixing local, NVIDIA, and OpenAI-compatible behavior without a canonical Nexus policy layer.
+4. Route success/failure is not being scored with Nexus trust or evidence logic.
+5. The router can crash on provider stream failures, turning partial degradation into full interruption.
+
+So the issue is not just "bad provider uptime." It is architectural mismatch.

+## Where The Non-Linear Trust System Fits
+
+The canonical trust engine is already present in:
+
+- `src/nexus_os/governor/trust_scoring.py`
+
+This is the right place to drive route trust.
+
+Do not use legacy Bayesian trust as the main route-decision engine.
+
+Map routing outcomes into lane-scoped scoring inputs.
+
+Suggested route-facing interpretation:
+
+- `Q`: quality confidence from evidence bundle quality
+- `n`: supporting evidence count
+- `U`: usefulness / success value of the route
+- `R`: regression / failure severity
+- `D_plus`: positive over-delivery or resilience contribution
+- `D_minus`: under-delivery / latency or availability harm
+
+Then each provider/model family, joker lane, or runtime lane can accumulate trust over time.
+
+Examples:
+
+- `joker_opus` can have strong trust for implementation and synthesis
+- `joker_grok` can have strong trust for research and fast exploratory synthesis

+- `openrouter/free` can be allowed only in low-risk research lanes if quality confidence is low

+Nexus should reason about:

+- model family
+- provider instance

+Any future router or relay layer must use:

+
+`modelrelay` auto-update should not be allowed to mutate the runtime baseline silently.

+- freeze or manually control upgrades

+### 5. Move secret handling out of plaintext router config over time
+
+`~/.modelrelay.json` currently behaves like a concentrated secret bundle.

+Nexus should evolve toward:
+
+- environment-injected keys
+- OS secret store

+## Recommended Scoring Stack For Route Selection
+
+Final route choice should not be "fastest benchmark wins."
+
+It should be something like:
+
+`route_score = policy_gate * trust_weight * health_weight * evidence_weight * cost_weight * latency_weight * availability_weight`
+
+Where:
+
+- `policy_gate`
+  - hard allow/deny by lane and data sensitivity
+- `trust_weight`
+  - comes from `trust_scoring.py`
+- `health_weight`
+  - real-time success/error/timeout window
+- `evidence_weight`
+  - normalized benchmark and route evidence from DoppelGround / ReviewGround
+- `cost_weight`
+  - token or spend sensitivity
+- `latency_weight`
+  - recent p50 / p95 performance
+- `availability_weight`
+  - circuit-breaker / cooldown state
+
+This is the sophisticated router Nexus actually needs.
